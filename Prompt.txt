# Warmup Control Center — Desktop Application

## 1. PROJECT OBJECTIVE

Build a production-quality native Windows desktop application called **Warmup Control Center**.

The application is a centralized control, monitoring, and analytics layer for email warmup infrastructure.

The application must connect to multiple MailWizz installations through the MailWizz API, automatically discover their delivery servers/mailboxes, synchronize MailWizz campaign/sending information, receive inbox-placement information from an existing Python inbox-checker worker, combine both datasets, and provide mailbox-level warmup intelligence.

The application must NOT replace MailWizz.

MailWizz remains the source of truth for:

* Sending mailboxes / delivery servers
* Campaigns
* Sending activity
* Delivery information
* Bounce/defer/error information
* MailWizz customer information

The desktop application becomes the source of truth for:

* Unified monitoring
* Historical warmup analytics
* Mailbox-level health
* Joined sending + placement information
* User-specific configuration
* Cross-MailWizz visibility

The key product question the application must answer is:

> "What is happening to each individual sending email ID?"

The user must be able to drill down from:

```text
Overall warmup
    ↓
Campaign
    ↓
Sending mailbox
    ↓
Individual send event
    ↓
Recipient
    ↓
Inbox / Spam / Promotions / Not Found
```

# 9. MAILWIZZ SYNCHRONIZATION

This is the FIRST major integration to implement.

Create:

```text
integrations/mailwizz/
    mailwizzClient.ts
    deliveryServers.ts
    campaigns.ts
    analytics.ts
```

Initially implement only:

```text
getDeliveryServers()
```

Then create:

```text
mailwizzSync.service.ts
```

The synchronization algorithm must be:

```text
1. Call MailWizz delivery-server API.

2. Receive all delivery servers.

3. For each delivery server:
      If not in database:
          create mailbox

      If already in database:
          update current information
          preserve historical data

4. Find previously known mailboxes that are no longer returned.

5. Mark those mailboxes:
      status = dropped

6. Never delete their historical records.

7. Save:
      last_sync_at
```

Make synchronization idempotent.

Running Sync twice must NOT create duplicates.

Use MailWizz delivery-server IDs as unique identifiers within the appropriate MailWizz connection/user scope.

# 15. WARMUP CASES

Support these six cases:

```text
CASE 1
50 Workspace → 15 Employee Tests

CASE 2
25 SMTP → 15 Employee Tests

CASE 3
50 Workspace → 50 Gmail Seeds

CASE 4
25 SMTP → 50 Gmail Seeds

CASE 5
25 SMTP → 50 Workspace

CASE 6
50 Workspace → 25 SMTP
```

Do not hardcode the account counts.

The case definition should be configurable.

Important rules:

### Employee tests

If mail lands in Spam:

```text
DO NOT MOVE IT
```

This is the litmus test.

### Gmail seeds

If mail lands in Spam:

```text
MOVE TO INBOX
```

Reply behavior may be implemented later.

### Cases 5 and 6

Replies can be treated as warmup signals.

### Cases 1–4

Do NOT treat replies as warmup evidence.

These distinctions must be represented in configuration/business rules.

CONNECT MAILWIZZ #2
CONNECT MAILWIZZ #3
  ↓

  ↓
75+ MAILBOXES DISCOVERED
  ↓

  ↓
MAILWIZZ SEND DATA
        +

        ↓
UNIFIED DATABASE
        ↓
WARMUP CONTROL CENTER
        ↓
Dashboard
        ↓
Mailbox
        ↓

        ↓

The final product is therefore a **Warmup Control Center**, not another MailWizz clone.

> **Give the user complete, mailbox-level visibility into email warmup by joining what MailWizz says happened during sending with what actually happened inside the receiving mailbox.**
